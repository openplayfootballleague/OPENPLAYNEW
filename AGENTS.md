# Open Play engineering instructions

## Product direction
Build Open Play as a production-grade football league platform, not a static marketing demo. The public site, player experience, captain workflows and administrator dashboard must share one coherent design system and domain model.

## Technical foundations
- TanStack Start with React and TypeScript.
- Vite build pipeline and Cloudflare Workers deployment.
- Supabase for Postgres, Auth, Storage and server-side functions when the correct new project is connected.
- Stripe for payments when payment integration is implemented.
- Keep dependencies pinned and commit the package lockfile generated by the chosen package manager.

## Non-negotiable engineering rules
- Never invent successful authentication, payments, registrations, uploads, emails or database writes. Show truthful loading, success and failure states.
- Never put Supabase secret/service-role keys or payment secrets in browser code, source control or public environment variables.
- Enforce permissions on the server and in database RLS. Hiding a button is not authorization.
- Validate all inputs on the server. Treat webhook events as untrusted until signatures are verified; make payment processing idempotent.
- Preserve audit history for privileged administrative actions.
- Use accessible semantic HTML, keyboard support, responsive layouts and clear empty/loading/error states.
- Keep business logic out of presentation components. Prefer typed domain services and reusable UI components.
- Do not introduce mock data into production flows. If fixtures are needed for design work, isolate and label them as preview-only.
- Do not recreate the official Open Play logo. Use the supplied official asset once it is added to the repository.
- Do not deploy production changes without a successful build and explicit verification.

## Product rules
- Browsing public league information must work without an account.
- Account creation is separate from player registration, team membership, captain status and administrator access.
- Roles and permissions must be assigned and checked securely server-side.
- 6-a-side team sheets: exactly 6 starters and up to 3 substitutes.
- 7-a-side team sheets: exactly 7 starters and up to 4 substitutes.
- Squad numbers are optional.
- Archived seasons are read-only and retain their historical records.
- Existing payment requests retain their original fee snapshot if future fees change.
- The administrator experience prioritizes a clear overview, quick actions and a prominent Needs Attention queue. Registers should be searchable, simple edits inline, and complex records in side panels.

## Visual direction
- Public experience: premium editorial football aesthetic, charcoal surfaces, warm orange accents, visible pitch greens and cinematic football imagery.
- Admin experience: clean, professional, calm, high-clarity interface, especially on iPad, with a strong task centre.
- Use the official orange Open Play brand asset; do not substitute a generated mark.
